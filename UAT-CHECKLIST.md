# UltiEconomy — UAT Checklist

This document is the executable companion to `FEATURES.md`: one row per feature stating the
steps to exercise it and the observable truth that proves it works. It is an internal reference
for real-machine verification, not user-facing documentation.

> Batches are dispatched at 60 rows or fewer, and a batch never spans two repositories. There are
> exactly two legitimate exits to `human-uat-pending`: a row needing the pixel layer while the
> real-client harness is not ready, and a row needing personal credentials. Every other row must
> reach `pass`, `fail`, or `blocked`.

## Conventions

- **Columns:** `ID`, `Preconditions`, `Steps`, `Expected`, `Layer`, `Covers`.
- **ID:** cites its `FEATURES.md` ID verbatim. A negative case suffixes the checklist ID only, as
  `.neg-<slug>` — a negative case still tests the same feature, so the base ID is unchanged.
  A second row exercising a different non-failing path of the same feature suffixes `.<slug>`
  with no `neg-`, because calling a passing path negative would misreport what the row asserts
  (the same clause as the UltiKits checklist's). Rows using it:
  `ultieconomy.scheduled.interest-payment.reload-interval`,
  `ultieconomy.scheduled.leaderboard-refresh.reload-interval`, and the four `.primary` rows that
  name the primary currency on a currency-named path (`ultieconomy.money.balance-currency.primary`,
  `ultieconomy.note.create-currency.primary`, `ultieconomy.admin.give-currency.primary`,
  `ultieconomy.placeholder.currency-scoped.primary`; UltiKits/UltiEconomy#25), and
  `ultieconomy.persistence.primary-wallet-merge.stale-claim` (the merge taken over from a server
  that stopped holding its claim; UltiKits/UltiEconomy#25).
- **Layer**, copied verbatim from the real-client acceptance tooling's fixed vocabulary: `protocol`,
  `java-client`, `os-input`, `pixel`, `server`, `human`. This module has no panel-facing surface,
  so no row below carries `human`.
- **Covers** back-references a GUI class excluded from the JaCoCo coverage gate; left blank when no such class
  applies. UltiEconomy has no GUI class excluded from the coverage gate (it ships no GUI page), so every
  row below leaves `Covers` blank.
- A row whose Preconditions cite a prior row's checklist ID must appear after that row in file
  order — asserted mechanically: for every row, every checklist ID literally cited in its
  Preconditions cell must have a strictly smaller line number in this file than the row citing it
 . A Preconditions cell that merely *describes* a state to set up (e.g. "a
  second, non-primary currency configured") without citing another row's ID by name is not
  subject to this check.
- **Expected** must name an observable truth — an exact chat line, a log line, a database row —
  and never the words "it works". **This document is English-only — a raw Chinese message
  literal is never reproduced inline.** Every chat and console line this module writes goes through
  its language catalogue with an ASCII key (the 23 keys UltiKits/UltiEconomy#14
  found missing are in both catalogues), so a row quoting a line carries `language: en`. For a row
  whose English text was introduced or changed by this release, the session also moves
  `plugins/UltiTools/pluginConfig/UltiTools-Economy/lang/` aside before the start so the jar's
  catalogues are extracted fresh (an upgraded install never refreshes an extracted language file,
  UltiKits/UltiTools-Reborn#459).
- **Multi-currency precondition:** this module ships exactly one currency by default
  (`config/currencies.yml`'s single `coins` entry, marked `primary: true`). Every row below whose
  ID ends `-currency` needs a SECOND, non-primary currency added to `config/currencies.yml` before
  it can be exercised at all — stated in that row's own Preconditions, not cited from a shared
  row, since adding a currency is a file edit, not a feature this document gives its own
  checklist row (see `## Configuration` below for why).
- **Config-per-file rule, narrowed for this module's own layout:** UltiEconomy ships two
  yml resources — `config/config.yml` (the module's one `@ConfigEntity`-bound file) and
  `config/currencies.yml` (read directly via `YamlConfiguration`, not `@ConfigEntity`-bound). By
  design ("exactly one config row for the single `@ConfigEntity`
  class"), this document carries exactly ONE config-per-file row, `ultieconomy.config.config-yml`,
  whose Steps exercise BOTH shipped files in the same pass — they load during the same server
  startup with no interdependent ordering, and `currencies.yml`'s own single row in `FEATURES.md`
  (`ultieconomy.config.currencies.currencies`) has no command surface of its own to test
  independently; the only way to exercise it at all is by editing the file and observing a
  currency-aware command, which the config-per-file row already does.

## Scheduled tasks

These rows read the boot log's `Registered config-bound @Scheduled task: …` INFO line, which the
framework's `TaskManager` prints once per task it registers, and count it — a second copy of a task
after `/ul reload` is the failure these rows exist to catch, because a second interest task pays
twice. Both intervals are config keys (`interest.interval`, `leaderboard.update-interval`, in
seconds) bound through UltiTools 6.3.0 (UltiKits/UltiTools-Reborn#531); a reload that changes one
logs `rescheduled config-bound @Scheduled task …` instead of registering anything.
Balances are read with `/eco check <player>` from console (`language: en`: its body lines read
`<player>'s balance: …`, `<player>'s bank balance: …` and `Total wealth: …`). "A's bank reads X"
below means the bank line — the second body line — ends with the formatted amount X, which carries the currency symbol and thousands separators
(`$10,000.00`).
